# DiPlay 导航数据实验记录 v49

入口：设置 → 高级 → 预览导航信息（实验性）。默认关闭；开启后立即接入进程内 iAP2 记录器，不改变现有导航输出、订阅、认证或路线选择。离开设置继续记录；进程重新启动后，如果开关仍开启，会新建采集目录，旧文件保留。进程被杀或断电期间无法记录。

## 下次上车

1. 安装 v49（包名及签名沿用 v48），打开高级设置的记录开关，确认预览中 `recording=true`、`error=none`。最好在连接 iPhone 之前开启；已经连接也能记录之后到达的消息，但不会补发此前已收到的数据。
2. 连接 CarPlay，在 iPhone 官方高德中开始导航。预览应出现 RX 0x5201/0x5202/0x5204 等实际收到的消息；具体类型取决于发送端。
3. 分别更改目的地、切换另一条路线、结束并重新开始导航。操作后用预览的“标记操作”按钮记录时间点，或另记操作时间。记录不会去控制手机导航。
4. 回到高级设置关闭记录，等待写入结束后，点击“导出全部导航记录（ZIP）”。正常保存到 Download/DiPlay；车机不支持公开下载目录时，文件保留在应用私有目录，并提供分享入口。导出失败不删除原始记录。
5. 带回 ZIP 即可分析。不要只截图预览；预览有意只显示摘要，ZIP 中原始帧不截断、不抽样、不去重。

## 记录内容及边界

- 在 Iap2Session 的 RX/TX 帧层采集，早于路名/箭头解码。保留所有 `0x5200..0x52ff` 消息的完整 CSM 编码（六字节头及 body），包括未知编号、重复 TLV、未知参数以及 TLV 结构异常的 body。CSM 分帧器已经丢弃的无效链路字节不在范围内。
- 每条记录有 UTC 毫秒、进程内单调时钟、递增序号、连接通道、linkId、消息编号、长度；原始 CSM 用 hex 保存，并附 SHA-256。
- 有线、无线 RFCOMM、无线 iAP 隧道均接入；连接准备/关闭/异常、开启/关闭记录及手动标记单独记录。
- 其他 CSM 消息仅保存 ID、名称、长度、时间，不保存认证、音乐、电话等非导航负载。未知导航协议若使用 0x52xx 之外的编号，只能从消息清单发现其出现，不能从这份记录恢复其负载。
- 不采集视频帧、独立文件传输中的路口图/资源、网络原始包；不新增 Route Sharing 能力宣告或协议协商。收到传统转向数据不代表支持路线坐标共享；没有坐标也不能证明高德没有发送到其他通道。
- 现有代码中的 maneuver index 是转向指令索引，不应当作高德 naviRouteID。要重绘滚动路线，需要实际证据证明有路线几何、车辆定位/进度和路线变化；周边路网还需要额外几何。

## 存储与完整性

原始目录：应用 files/navigation-captures/<timestamp-uuid>/events.jsonl。每次启用独立目录，所有已有录制都会打包；不自动删除旧录制。每条记录落盘并同步文件，仍无法保证断电时最后一条一定完整，分析器会检查。

录制总量达到 256 MiB（跨录制累计），或写入队列溢出、存储错误，会停止记录并报告不完整，不会静默截断、覆盖历史或阻塞 CarPlay 接收线程。队列最多 256 条；终止状态保留原因（磁盘彻底不可写时可能只表现为缺少 capture_end）。额外终止标记可能略超容量上限。达到上限需先导出备份，再通过 ADB 管理采集目录；应用不提供静默清理。

记录开关保存启用偏好，异常停止后本次录制不会自动重开；下次进程启动会尝试开启新的录制（容量已满则失败并关闭偏好）。预览应检查 recording/error，而不只看开关。

导出为流式 ZIP，不拼接为普通诊断的大字符串，不经过诊断脱敏/截断。导出等待调用时已入队消息落盘，之后按完整记录边界锁定文件长度；进行中的录制继续增长。在线导出缺少 capture_end 属于进行中快照，建议停止后再次导出获取明确的结束状态。路名/位置等实际收到的数据会保留在 ZIP 中。

## 离线分析

```sh
python3 analyze-navigation-capture.py DiPlay-navigation-xxx.zip --out analysis
```

生成 summary.json（会话、编号计数、标记、完整性问题）与 decoded.jsonl（每条消息、按原顺序展开的完整 TLV、已知字段、未知字段原始 hex、参数位置变化）。分析器不会把未知整数猜成坐标。标记时间可对照当前路线/指令更新，原 ZIP 保留不动。

测试使用合成数据，仅验证记录、存储与解析行为；实车 iPhone 高德字段范围、坐标可用性及断线恢复需本次上车记录确认。
